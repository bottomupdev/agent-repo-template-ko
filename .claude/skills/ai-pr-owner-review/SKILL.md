# AI PR Owner Review

## 목적

이 스킬은 제품 오너, 창업자, 테크 리드, 메인테이너가 AI가 작성한 PR을 감독할 수 있을 만큼 깊이 이해하도록
돕습니다. 구현과 제품/아키텍처 트레이드오프를 설명합니다. 대화형 teach-back(오너가 자기 말로 다시 설명해
보게 하는 확인 질문)은 오너가 요청하거나 명시적으로 이미 존재하는 게이트가 요구할 때만 진행합니다. AI가
작성했다는 사실, 변경이 사소하지 않다는 사실, 일상적인 머지 요청만으로는 그런 게이트가 생기지 않습니다.

명시적인 오너 결정과 위험 수용 게이트는 지키되, 같은 작업과 범위에 대해 이미 기록된 결정은 재사용합니다.
저장소가 PR별 전달 기록이나 결정 기록을 둔다면, 오너 결정, 운영 절차, 중대한 위험 수용을 남겨야 할 때 그
기록에 teach-back 질문과 모범 답안을 적습니다. 일상적인 전달은 그 항목을 짧은 이유와 함께 `N/A`로 표시할
수 있습니다. 기록을 쓰는 것 자체가 오너의 답을 기다려야 한다는 뜻은 아닙니다.

## 핵심 절차

1. 리뷰 대상을 확정합니다.
   - PR, 브랜치, 커밋 범위, 로컬 diff를 확인합니다.
   - `AGENTS.md`, `CLAUDE.md`, `CONTRIBUTING.md`, 아키텍처 문서, 결정 기록, 제품 명세, 이슈 설명, PR 템플릿
     같은 저장소 지침을 확인합니다.
   - GitHub 도구를 쓸 수 있고 사용자가 PR을 지정하면 PR 메타데이터, 바뀐 파일, 리뷰 코멘트, 연결된 이슈를
     봅니다.

2. 구현을 지도로 그립니다.
   - PR을 계층별로 요약합니다: 제품 흐름, UI/클라이언트, 백엔드/API, 데이터 모델, 스토리지, 인증/접근 제어,
     백그라운드 작업/네이티브 코드, 테스트, 문서, 운영.
   - 각 계층을 그 스택이 처음인 개발자도 알아듣게 쉬운 말로 설명합니다.
   - 중요한 파일과 각 파일의 역할을 짚습니다.
   - 사용자 동작에서 영속 상태로, 다시 사용자에게 보이는 출력으로 이어지는 주요 런타임 경로를 설명합니다.

3. 기준 결정과 대조합니다.
   - PR이 지켜야 하는 제품 약속, 아키텍처 경계, 개인정보/보안 제약, 비목표(non-goal)를 짚습니다.
   - 구현이 그 제약을 코드, 테스트, 데이터베이스 정책, 문서 중 어디서 강제하는지 짚습니다.
   - 의도된 MVP 한계와 실수로 생긴 공백을 구분합니다.

4. 오너가 꼭 이해해야 할 지점을 찾습니다.
   - 앞으로의 작업을 지휘하려면 오너가 알아야 할 개념을 나열합니다.
   - 되돌릴 수 없거나 바꾸기 비싼 결정을 강조합니다.
   - 이후 에이전트가 실수로 제품 방향을 어길 수 있는 곳을 강조합니다.
   - 머지 차단 요소, 머지 후 후속 작업, 열린 제품 결정을 구분합니다.

5. 대화형 teach-back이 요청되었거나 명시적으로 필요하면 teach-back 질문을 합니다.
   - 오너가 설계를 자기 말로 설명하게 만드는 간결한 질문을 합니다.
   - 제품 약속, 데이터 흐름, 신뢰 경계, 수명주기/상태 기계, 실패 처리, 보안/개인정보, 테스트 공백, 향후 확장성을
     다룹니다.
   - 사소한 지식 확인은 피합니다. 오너가 앞으로의 변경을 감독할 수 있는지 드러내는 질문을 고릅니다.

6. 오너가 답하면 평가합니다.
   - 올바른 이해는 바로 확인해 줍니다.
   - 오해는 구체적인 설명으로 바로잡습니다.
   - 제품 방향, 머지 안전성, 이후 에이전트 작업에 영향을 주는 경우에만 빠진 뉘앙스를 덧붙입니다.
   - 답에서 문서 공백이 드러나면 정확히 어떤 문서, 결정 기록, 이슈, PR 템플릿을 고칠지 권합니다.

7. 행동 중심의 머지 준비 요약으로 마칩니다.
   - 남은 오너 감독 요구사항이 있으면 적습니다. 답이 없다고 해서 이해했거나 승인했다고 추론하지 않습니다.
   - 남은 차단 요소가 있으면 나열합니다.
   - 머지 후에 해도 되는 후속 이슈나 점검을 나열합니다.
   - 검증하지 못한 점검은 명시적으로 밝힙니다(PR 템플릿이 있으면 `## 확인하지 못한 것`과 대조합니다).

## 출력 구성

PR을 처음 설명할 때는 사용자가 달리 요청하지 않으면 다음 구성을 씁니다.

- PR의 전체 목적
- 아키텍처와 파일 지도
- 런타임 흐름
- 중요한 제품/개인정보/보안 경계
- 테스트와 검증 커버리지
- MVP 한계와 후속 작업
- 대화형 teach-back이 요청되었거나 명시적으로 필요할 때, 오너를 위한 teach-back 질문

오너의 답을 평가할 때는 다음 구성을 씁니다.

- 올바르게 이해한 것
- 바로잡을 점이나 빠진 뉘앙스
- 오너가 꼭 가져가야 할 핵심
- 권장하는 문서/이슈/템플릿 갱신

## 리뷰 휴리스틱

AI가 작성한 PR에서 특히 중요하게 봅니다.

- 코드가 제품 약속과 맞는가, 아니면 제품을 조용히 바꿨는가?
- 신뢰 경계가 명시적이고 테스트되었는가?
- 수명주기 상태가 분명하고, 잘못된 전이를 막는가?
- 개인정보에 민감한 값이 적절히 로그, 분석, URL, 스토리지, 클라이언트 코드에서 빠져 있는가?
- 인터페이스를 약속한 곳에서 구현이 구체 공급자에 기대고 있지는 않은가?
- 정상 경로만이 아니라 실패 경로와 정리 경로도 설계되었는가?
- 테스트가 동작과 엣지 케이스를 지키는가, 아니면 주로 목(mock)을 검증하는가?
- 수동 검증 공백이 이슈로 만들 수 있게 명명되어 있는가?
- 영속적인 결정이 바뀌었을 때 문서와 결정 기록이 갱신되었는가?

## 질문 은행

PR에 맞게 다듬어 씁니다.

- 이 PR은 어떤 제품 약속을 지키거나 진전시키나요?
- 어떤 데이터가 시스템에 들어오고, 어디서 변환되고, 어디에 저장되나요?
- 구현의 어느 부분이 공급자 종속적이고, 어느 부분이 추상화되어 있나요?
- 일반 인증 사용자가 직접 할 수 있는 것은 무엇이고, 서버 쪽 권한 있는 경로가 필요한 것은 무엇인가요?
- 절대 저장, 로깅, 업로드, 노출되면 안 되는 민감한 데이터는 무엇인가요?
- 어떤 수명주기 상태가 있고, 각 상태에서 어떤 작업이 허용되나요?
- 작업이 중간에 실패하면 어떻게 되나요?
- 어떤 테스트가 고위험 경계를 증명하고, 어떤 점검이 아직 수동인가요?
- 어떤 한계는 MVP에서 받아들일 수 있고, 어떤 것은 베타나 머지 전에 고쳐야 하나요?
- 오너 리뷰 없이 맡기면 위험할 향후 AI 에이전트 작업은 무엇인가요?

## 기본 규칙

- 테스트가 통과한다고 PR이 옳다고 가정하지 않습니다.
- 모든 파일로 오너를 압도하지 않습니다. 멘탈 모델과 위험을 지닌 세부를 우선합니다.
- 불확실성을 숨기지 않습니다. 추론과 검증되지 않은 주장은 그렇다고 표시합니다.
- 사용자가 명시적으로 구현 작업을 요청하지 않으면 코드를 만들거나 수정하지 않습니다.
- 추상적인 안심보다 구체적인 파일 참조와 상태 전이를 우선합니다.
