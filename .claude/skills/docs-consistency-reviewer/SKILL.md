description: pull request(PR)의 문서, ADR/결정 기록(decision record), 범위, 제품, 아키텍처 정합성을 리뷰합니다(docs review, documentation consistency review). 문서가 구현된 동작과 맞는지, 결정이 영속적으로 기록되었는지, 열린 질문이 해결된 것처럼 적히지 않았는지, 프로젝트/이슈 추적 문서가 정확한지, 이력/참고 문서가 기준 문서가 아님을 분명히 하는지에 초점을 둔 읽기 전용 리뷰를 요청받을 때 사용합니다. 사용자가 명시적으로 문서/제품/아키텍처 정합성으로 범위를 정하지 않는 한 일반 코드 정확성, 보안, CI, 구현 리뷰에는 쓰지 않습니다.

# Docs Consistency Reviewer

이 스킬은 PR의 문서와 관련 구현 근거에 대한 읽기 전용 정합성 리뷰를 합니다.

## 엄수 규칙

- 파일을 수정하지 않습니다.
- 사용자와 직접 마주한 리뷰는, 사용자가 처음 요청이나 세션의 상시 지침에서 게시를 명시적으로 허락했을 때만
  PR, 이슈, 리뷰 코멘트를 올릴 수 있습니다. 리뷰 뒤에 다시 요청받을 필요는 없습니다. 위임된 서브에이전트로
  실행되는 리뷰어는 읽기 전용을 유지하고, 게시하는 쪽에 코멘트 문안을 돌려줍니다.
- 리뷰 범위는 문서, 결정 기록, 제품/범위 주장, 아키텍처 주장, 프로젝트 추적 정합성으로 한정합니다.
- 문서 정합성 문제를 직접 증명하거나 반박하는 경우가 아니면 일반 버그 리뷰, 보안 리뷰, CI 디버깅, 서식,
  구현 정리로 넓히지 않습니다.
- 사용자가 정한 리뷰 범위를 기준으로 삼습니다. 프로젝트 전용 불변 조건을 주면 그것을 검증하되, 스킬 안에
  박아 넣지 않습니다.

## 정식 지적 채택 기준 (Formal Finding Admission)

이 리뷰어는 공용 채택 기준을 따릅니다. 이 스킬을 템플릿 저장소에서 가져왔다면 전체 원본은 그 저장소의
`.claude/skills/finding-admission.md`입니다. 아래 요약만으로도 단독으로 쓸 수 있습니다.

정식 지적(formal finding)은 이 리뷰어 영역의 구체적 위험을 짚고, 다음 채택 기준 중 하나 이상을
만족해야 합니다.

1. 변경이 합의된 요구사항, 결정 기록, 계약, 명시적 불변 조건(invariant)을 위반한다.
2. diff가 사용자, 운영자, 시스템에 재현 가능한 실패 경로를 만든다.
3. 보안, 개인정보, 권한, 데이터 손실, 데이터 손상, 되돌릴 수 없는 수명주기 위험을 만들거나 남겨 둔다.
4. 이미 구속력이 있는 릴리스 또는 인수(acceptance) 게이트를 막는다.
5. 기준 브랜치(base branch) 대비 동작을 회귀시킨다.
6. 같은 운영 실패가 두 번째로 관찰되었다.
7. 바뀐 고위험 동작에, 올바른 동작과 위험한 회귀를 구분해 주는 변별력 있는 테스트(load-bearing test)가 없다.
8. 합의된 측정 가능 목표를 재현 가능한 근거로 놓친다.

모든 정식 지적에는 위반한 불변 조건이나 위험 경계, 추적한 실패 시퀀스나 관찰 가능한 결과, 근거나 범위가
정해진 반증 절차(falsification step), 심각도(`Must fix before merge` 또는 `Can track after merge`),
확신도(`High`/`Medium`/`Low`), 가장 작고 비례에 맞는 수정 방법을 적습니다. 확신도와 심각도는 별개이므로
모든 지적에 두 축을 함께 적습니다.

확신도가 낮은 가설은 예외 범주(보안, 개인정보, 데이터 손실, 되돌릴 수 없는 권한 변경, 동시 작성자/단일
작성자 위반)에 속하고 구체적인 반증 절차가 있을 때만 채택합니다. 기준 밖 항목(스타일, 이름 짓기, 합의된
목표 없는 확장성 추측, 추적한 위험 경로 없는 유지보수성 취향, 바뀐 불변 조건에 이미 변별력 있는 테스트가
있는데 덧붙이는 테스트 아이디어, 주변 정리, 근거 없는 벤더 가설)은 참고 관찰(non-finding observation)로
따로 적을 수 있고, 참고 관찰에는 분류나 처리 의무가 없습니다. 커버리지를 증명하려고 지적 목록을 부풀리지
않습니다. 정식 지적이 없고 남은 검증 공백을 명시한 결과도 유효합니다.

영역별 적용: 실행하는 에이전트를 잘못 이끌거나 불변 조건을 잘못 적은 문서/코드 모순은 채택 기준 1을
만족합니다. 잘못 이끄는 경로를 추적하지 못한 문구 취향은 참고 관찰입니다.

**반례 점검.** 의심스러워 보이는 패턴이 있으면 기각하기 전에 구체적인 반례를 직접 만들어 봅니다. 체계적인
체크리스트 리뷰가 여전히 주된 방법이고, 이것은 기각을 점검하는 장치일 뿐 공격 우선 리뷰로 바꾸는 것이
아닙니다.

## 맥락 수집

정합성을 판단하기 전에 프로젝트의 에이전트 지침과 기준 문서를 읽습니다. 흔한 예:

- `AGENTS.md`, `CLAUDE.md`, `.cursor/rules` 같은 에이전트 지침 파일이나 저장소별 대응 파일
- 현재 상태 또는 개요 문서
- 결정 로그, ADR, RFC, 아키텍처 결정 기록, 설계 문서
- 제품 명세, MVP/범위 문서, 로드맵, 스코어카드, 추적 문서, 열린 질문 문서
- `docs/`, `architecture/`, `product/` 또는 그에 준하는 폴더 아래의 관련 문서

PR 메타데이터, 바뀐 파일 이름, 문서가 코드와 맞는지 확인할 만큼의 바뀐 구현 파일도 봅니다. 가능하면 GitHub
도구를 씁니다. 로컬 `git`, `gh`, 저장소 파일은 브랜치 상태, 프로젝트 보드/이슈 메타데이터, 파일 단위 diff
세부 같은 빈틈을 메울 때만 씁니다.

기본적으로 아카이브나 이력 폴더를 재귀적으로 읽지 않습니다. 이력 근거가 필요하면 저장소의 출처 색인이나
README 같은 안내 문서에서 시작해 필요한 파일만 엽니다.

## 리뷰 체크리스트

다음을 확인합니다.

- 현재 문서가 PR이 바꾸거나 의존하는 구현 동작과 일치한다.
- 영속적인 결정이 프로젝트의 결정 로그, ADR, RFC 또는 그에 준하는 기록에 반영되어 있다.
- 열린 질문이 다른 곳에서 실수로 확정된 결정처럼 제시되지 않는다.
- 확정된 구현 선택이 여전히 미해결 질문으로 남아 있지 않다.
- 제품 범위 문서가 저장소의 현재 범위 경계와 사용자가 명시한 불변 조건에 맞는다.
- 아키텍처 문서가 현재 경계, 소유권, 인터페이스, 향후 모듈화를 정확히 설명한다.
- 백엔드, 스토리지, 인프라, 공급자 선택이 현재/향후 상태를 올바르게 구분해 설명된다.
- 프로젝트 관리 문서가 구체적인 주장을 할 때 실제 PR, 이슈, 마일스톤, 라벨, 프로젝트 보드 메타데이터와
  일치한다.
- 아카이브, 리서치, 마이그레이션, 세션 요약 문서가 대체된 아이디어를 보존할 때 이력용이거나 기준 문서가
  아님을 분명히 표시한다.
- 저장소가 특정 종류의 코드 변경에 문서 갱신을 요구한다면(예: "언제 어떤 문서를 고치나" 표) PR이 그 갱신을
  했다. PR 템플릿이 있으면 `## docs` 섹션에 고친 문서나 해당 없음의 이유가 실제 diff와 맞게 적혀 있다.

## 심각도 기준

어느 심각도를 붙이든 먼저 정식 지적 채택 기준을 적용합니다. 아래 예시가 제외 대상인 관찰을 채택시키지는
않습니다.

이후 기여자나 에이전트를 현재 범위, 개인정보/안전 불변 조건, 합의된 아키텍처, 영속적인 결정, 프로젝트 실행
상태, 구현 경계에 대해 잘못 이끌 수 있으면 `Must fix before merge`로 표시합니다.

채택한 지적 가운데 구체적인 잔여 문서 정합성 위험이 머지를 막지 않으면 `Can track after merge`로 표시합니다.
잘못 이끄는 경로를 추적하지 못한 선택적 정리나 더 명확한 문구는 참고 관찰입니다.

파일이나 그 파일이 든 폴더가 기준 문서와 합의된 결정이 우선한다고 분명히 밝히고 있다면, 이력/참고 문구를
차단 요소로 보고하지 않습니다.

## 실무 절차

1. PR 번호, 저장소, 브랜치, 최신 head SHA를 확정합니다.
2. 사용자가 지정한 필수 문서와 저장소의 에이전트 지침을 읽습니다.
3. PR의 바뀐 파일 이름과 관련 diff/파일 내용을 봅니다.
4. 문서가 다루는 제품이나 아키텍처 경계를 정의하는 구현 파일을 표본으로 봅니다.
5. 문서가 구체적인 추적 주장을 하면 실제 메타데이터와 대조합니다.
6. 구현, 기준 문서, 결정 기록, 열린 질문, 추적 문서, 이력/참고 문서를 비교합니다.
7. 지적을 먼저 둔 간결한 리뷰를 냅니다.

## 출력 형식

지적을 먼저, 심각도 순으로 반환합니다.

지적마다 다음을 포함합니다.

- 짧고 안정적인 제목.
- 상태: `Must fix before merge` 또는 `Can track after merge`.
- 확신도: `Confidence: High`, `Confidence: Medium`, `Confidence: Low`.
- 가능하면 파일 경로와 줄 번호.
- 불일치 내용.
- 제품/아키텍처 정합성에서 그것이 중요한 이유.
- PR 코멘트 문안.

지적 뒤에 다음을 넣습니다.

- `머지 전 고칠 문서(Docs to update before merge)`: 정확한 파일 목록, 또는 `None`.
- `검증 노트(Verification notes)`: 무엇을 살펴봤는지와 한계. 예: 볼 수 없던 프로젝트 보드 필드, 커넥터 제약,
  로컬 체크아웃 불일치.

차단 요소가 남지 않았으면 그렇다고 분명히 말하고, 여전히 조치 가능한 잔여 can-track 항목만 나열합니다.

## 사용자 프롬프트 개선 제안

사용자가 리뷰 프롬프트를 주면 프로젝트 전용 체크리스트는 그대로 두되, 도움이 되면 다음을 추가하도록
권합니다.

- 저장소와 PR 번호 또는 URL을 명시한다.
- 실제 GitHub 이슈/프로젝트 메타데이터를 확인할지 밝힌다.
- 먼저 읽을 기준 문서와 이력/아카이브 안내 규칙을 나열한다.
- 프로젝트의 현재 범위 불변 조건을 명시한다.
- 기존 PR 코멘트를 이미 처리된 것으로 볼지 밝힌다.
- 출력에 코멘트 문안만 넣을지, 최종 판정도 넣을지 밝힌다.
