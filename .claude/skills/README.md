# 리뷰어 스킬

Claude Code와 Codex에서 쓰는 읽기 전용 AI 코드 리뷰 스킬입니다. 스킬 하나가 좁은 영역을 맡은 전문 리뷰어
한 명이고, 각자 체크리스트를 갖되 무엇을 지적으로 인정할지는 공용 규칙 하나를 따릅니다. 하나만 돌려도 되고,
같은 PR에 여러 개를 돌려 결과를 합쳐도 됩니다.

| 스킬 | 리뷰하는 것 |
| --- | --- |
| `engineering-reviewer` | 아키텍처, 신뢰성, 효율, 확장성, 유지보수성, 머지 준비 상태. 추측성 구조와 중복된 원본(source of truth)도 점검합니다. |
| `test-coverage-reviewer` | 바뀐 동작이 회귀했을 때 테스트가 실제로 잡아내는지. |
| `security-reviewer` | CI 워크플로와 에이전트 도구 권한을 포함한 구체적인 보안·개인정보 위험. |
| `backend-api-reviewer` | 인증, 권한, 소유권, 데이터 접근 정책, 수명주기 전이, 스토리지와 signed URL, 공개 토큰, 오류 의미. |
| `docs-consistency-reviewer` | 문서, 결정 기록, 범위, 아키텍처 주장이 코드가 하는 일과 맞는지. |
| `protocol-walkthrough-reviewer` | 에이전트 프롬프트, 런북, CI 워크플로를 페르소나 하나씩 글자 그대로 실행해 깨지는 곳 찾기. |
| `ai-pr-owner-review` | 게이트가 아닙니다. AI가 작성한 PR을 오너에게 설명하고 차단 요소와 후속 작업을 구분합니다. 원하면 teach-back 질문도 합니다. |

## 구성

```text
.claude/skills/<name>/SKILL.md            스킬 본문 (frontmatter: name, description)
.claude/skills/<name>/agents/openai.yaml  Codex 인터페이스 메타데이터 (표시 이름, 기본 프롬프트)
.claude/skills/finding-admission.md       공용 채택 기준 (원본)
.claude/skills/README.md                  이 파일
```

어떤 PR에 어떤 리뷰어를 돌릴지는 스킬이 아니라 프로젝트가 정할 일입니다. 이 템플릿으로 만든 저장소에서는
[docs/05-review.md](../../docs/05-review.md)에 있습니다. 그 파일이 없으면 아래 [기본 라우팅](#기본-라우팅)에서
시작합니다.

## 리뷰 원칙

- **읽기 전용.** 리뷰어는 읽고 보고합니다. 명시적으로 요청하지 않으면 파일 수정, 커밋, 코멘트 게시를 하지
  않습니다. 서브에이전트로 돌 때는 게시하는 쪽에 코멘트 문안을 돌려줍니다.
- **지적 먼저.** 출력은 심각도 순 지적으로 시작합니다. 요약과 "무엇을 봤는지"는 뒤에 짧게 둡니다.
- **모든 지적에 두 축.** 심각도(`Must fix before merge` 또는 `Can track after merge`)는 사실일 때 무슨 일이
  생기는지, 확신도(`High`, `Medium`, `Low`)는 리뷰어가 얼마나 확신하는지를 말합니다.
- **실패를 직접 구성.** 엔지니어링 리뷰어와 보안 리뷰어는 깨지는 시퀀스(경쟁 상태, 두 쓰기 사이의 크래시,
  악용 사례, 인젝션 경로)를 직접 만들어 근거로 보고합니다.
- **프로토콜을 실행.** 에이전트가 프로젝트를 돌린다면 프롬프트와 워크플로 파일도 코드입니다.
  `protocol-walkthrough-reviewer`는 이를 글자 그대로 읽는 적대적 해석자로서 읽고, 깨지는 페르소나와 단계를
  보고합니다.
- **변경분 중심 재리뷰.** 재리뷰는 PR 전체가 아니라 이전 지적과 새 변경분(delta)을 확인합니다.

## 채택 기준 요약

전체 기준은 [finding-admission.md](finding-admission.md)에 있습니다. 스킬 하나만 써도 동작하도록 각
`SKILL.md`에 최소한을 다시 적어 두었습니다.

- 지적은 여덟 가지 기준 중 하나를 만족해야 합니다: 합의된 요구사항이나 불변 조건 위반, 재현 가능한 실패 경로,
  보안·개인정보·권한·데이터 손실·되돌릴 수 없는 수명주기 위험, 구속력 있는 릴리스 게이트 차단, 기준 브랜치 대비
  회귀, 같은 운영 실패의 두 번째 발생, 바뀐 고위험 동작에 변별력 있는 테스트(load-bearing test) 부재, 합의된
  측정 목표 미달.
- 지적에는 추적한 실패 시퀀스, 근거나 반증 절차, 심각도, 확신도, 가장 작고 비례에 맞는 수정이 들어갑니다.
- 확신도가 낮은 가설은 보안, 개인정보, 데이터 손실, 되돌릴 수 없는 권한 변경, 동시 작성자 위반에 한해서만
  채택합니다.
- 스타일, 이름 짓기, 추측성 확장성, "테스트가 더 있으면 좋겠다"는 의무가 없는 별도의 참고 관찰 목록에 둡니다.
- 지적이 하나도 없는 것도 유효한 결과입니다.
- 채택한 지적은 모두 처리 결과 하나로 끝납니다: 커밋에서 고침, 이슈로 추적, 권한 있는 사람의 위험 수용,
  이유를 적은 인정 안 함.

## 설치

### Claude Code

이 템플릿으로 만든 저장소라면 할 일이 없습니다. Claude Code는 프로젝트의 `.claude/skills/` 아래 스킬을 자동으로
찾습니다. `agents/openai.yaml`, `README.md`, `finding-admission.md`는 무시합니다.

모든 프로젝트에서 쓰려면 사용자 디렉터리로 복사합니다.

```sh
mkdir -p ~/.claude/skills
cp -r .claude/skills/*/ ~/.claude/skills/
```

### Codex

스킬 폴더를 Codex 스킬 디렉터리(`$CODEX_HOME/skills`, 기본값 `~/.codex/skills`)로 동기화하고 Codex를 다시
시작합니다.

```sh
mkdir -p ~/.codex/skills
cp -r .claude/skills/*/ ~/.codex/skills/
```

스킬을 고친 뒤에는 다시 실행합니다. 설치하지 않아도 됩니다. 어떤 에이전트든 파일을 읽고 따르게 할 수
있습니다("`.claude/skills/security-reviewer/SKILL.md`를 읽고 그대로 따라 줘").

### 기존 저장소에 복사

스킬은 이 템플릿의 나머지 부분에 의존하지 않습니다.

```sh
mkdir -p .claude/skills
cp -r <템플릿 경로>/.claude/skills/. .claude/skills/
```

그다음 저장소에 라우팅 표를 두고([기본 라우팅](#기본-라우팅)이나 `docs/05-review.md`를 복사해 고칩니다),
에이전트 지침(`AGENTS.md`, `CLAUDE.md`)에 언제 리뷰어를 돌리는지 한 줄 적습니다.

## 실행

Claude Code:

```text
/engineering-reviewer PR 42를 head <sha>에서 리뷰해 줘
```

또는 평소 말로 요청합니다("이 브랜치 security review 해 줘"). Codex:

```text
$security-reviewer로 이 PR의 보안과 개인정보 위험만 리뷰해 주세요.
```

대상은 항상 정확히 줍니다: PR URL이나 번호, 브랜치, diff 범위, 가능하면 head SHA까지. 오래된 체크아웃 때문에
결과가 틀어지지 않게 합니다.

## 한 PR에 여러 리뷰어 돌리기

1. **등급을 정하고 라우팅합니다.** 리뷰 등급(tier) 하나를 고르고, 해당하는 라우팅 행을 모두 합칩니다. 등급이
   넓다는 이유만으로 무관한 리뷰어를 더하지 않습니다.
2. **독립적으로 돌립니다.** 리뷰어마다 같은 대상과 head SHA로 별도 서브에이전트를 띄워, 한 리뷰어의 관점이
   다른 리뷰어를 끌고 가지 않게 합니다. 모두 읽기 전용이라 병렬로 돌려도 됩니다. Claude Code에서는
   "이 브랜치에 engineering-reviewer와 security-reviewer를 각각 별도 서브에이전트로 돌리고 지적을 합쳐 줘"라고
   하면 됩니다.
3. **지적을 합칩니다.**
   - 표현이 달라도 근본 원인이 같은 지적은 묶습니다. 묶음마다 안정적인 제목 하나를 두고 어느 리뷰어가 올렸는지
     적습니다.
   - 묶음 안에서 가장 높은 심각도를 유지합니다. 확신도는 가장 강한 근거를 따릅니다(직접 구성한 실패 시퀀스가
     패턴 일치보다 강합니다).
   - 합친 목록에 채택 기준을 다시 적용합니다. 호스팅 리뷰 봇의 항목을 포함해 기준을 통과하지 못한 항목은 한 줄
     이유와 함께 채택하지 않음으로 한 번 기록합니다.
   - 채택한 지적마다 처리 결과 하나를 정해 PR 본문(PR 템플릿의 `## 리뷰` 섹션)에 기록합니다.
4. **변경분을 재리뷰합니다.** 수정 뒤에는 각 리뷰어에게 이전 head, 현재 head, 처리한 지적을 줍니다(아래
   프롬프트). 이 head에서 새로 라우팅된 리뷰어나 PR base가 바뀐 리뷰어는 전체 리뷰를 합니다.
5. **멈춥니다.** 깨끗한 라운드 한 번이면 그 head에서 리뷰가 끝납니다. 상한으로, 저장소 파일에 대한
   `Must fix before merge`가 없는 라운드가 연속 두 번이면 그 head에서 PR을 출시할 수 있습니다.

## 기본 라우팅

스킬만 복사해 쓰는 경우를 위한 기본값입니다. `docs/05-review.md`가 있으면 그 파일이 기준입니다.
`always`는 모든 구현 PR에서 돌리고, 나머지 행은 조건부입니다.

| 리뷰어 | 라우팅 조건 |
| --- | --- |
| `engineering-reviewer` | always |
| `test-coverage-reviewer` | 프로덕션 코드나 핵심 표면이 바뀜, 또는 테스트가 바뀜 |
| `backend-api-reviewer` | API 라우트, 인증, 권한, 데이터 접근 정책, 리포지토리, 스토리지 어댑터, 공개 토큰이나 링크 접근, 자원 수명주기 전이가 바뀜 |
| `security-reviewer` | 개인정보, 보안, 인증, 접근 정책, 토큰, signed URL, 스토리지, 로깅, 분석, 공개 링크가 바뀜; 사용자 데이터를 나르는 경계가 바뀜; 또는 CI나 에이전트 워크플로 표면이 바뀜 |
| `docs-consistency-reviewer` | 문서, 결정 기록, 범위, 아키텍처 주장이 바뀜; 코드 변경에 문서 갱신이 필요함; 또는 에이전트 프롬프트, 스킬, CI 워크플로가 바뀜 |
| `protocol-walkthrough-reviewer` | 에이전트 프롬프트, 스킬 파일, 런북, CI 워크플로, 그 밖에 에이전트나 러너가 실행하는 절차가 바뀜 |

| 등급(tier) | 분류 | 필요한 리뷰 |
| --- | --- | --- |
| `low-risk docs/tests` | 문서나 테스트만 바뀜. 동작, 핵심 표면, 절차, 권한 변경 없음 | `engineering-reviewer`; 테스트가 바뀌면 `test-coverage-reviewer`; 문서가 바뀌면 `docs-consistency-reviewer` |
| `ordinary code` | 회귀 위험이 있는 프로덕션 코드, 핵심 표면 없음 | `engineering-reviewer`, `test-coverage-reviewer`, 해당하는 전문 리뷰어 전부 |
| `critical surfaces` | 개인정보, 인증, 스토리지, 삭제, 마이그레이션, 권한, 동시성이나 복구, 플랫폼 간 계약, 에이전트나 CI 권한 | `ordinary code`와 같음 |

`ai-pr-owner-review`는 게이트가 아닙니다. 오너가 PR 설명을 원할 때 돌립니다. 엔지니어링 리뷰어는 선언한
등급과 라우팅이 diff와 맞는지 확인합니다. 저장소마다 라우팅 표는 하나만 원본으로 두고, 다른 파일은 그것을
가리킵니다. `engineering-reviewer`, `test-coverage-reviewer`, `security-reviewer`를 빼는 것은 의도적이고 리뷰를
거친 변경으로 다룹니다.

## 요청 프롬프트

```text
<PR URL, 브랜치, diff 범위>를 리뷰해 주세요.

Head SHA: <전체 SHA>
연결된 이슈나 요구사항: <URL 또는 "없음">
리뷰 등급(tier): <tier>

먼저 읽을 것: 저장소의 에이전트 지침(AGENTS.md, CLAUDE.md), 정확한 현재 head와 diff, 연결된 이슈와 그 이슈가
가리키는 문서, 지정한 리뷰어 스킬.

리뷰는 읽기 전용입니다. 파일을 수정하거나 코멘트를 올리지 마세요.
지적을 먼저 내고, 지적마다 짧고 안정적인 제목을 붙이고, .claude/skills/finding-admission.md 기준으로
채택하세요. 기준 밖 항목은 참고 관찰로 따로 적으세요. 지적마다 PR 코멘트 문안을 넣어 주세요.
```

재리뷰:

```text
<PR URL>을 재리뷰해 주세요.

이전에 리뷰한 head: <전체 SHA, 또는 "none - newly required">
현재 head: <전체 SHA>
그 리뷰 이후 base 변경: <none, 또는 이전 base -> 새 base>
정확한 변경분 범위: <이전 SHA..현재 SHA, 또는 "N/A">
처리한 지적:
1. <지적 제목>
이 변경분이 실질적으로 영향을 주는 불변 조건:
- <불변 조건>

이전 지적을 각각 Resolved, Still valid, Needs follow-up으로 분류하세요. 현재 head에서 변경분과 위에 적은 불변
조건을 확인하고, PR 전체를 처음부터 다시 훑지 마세요. 새 지적은 수정이 만든 회귀, 바로잡은 리뷰 입력이 여전히
위반인 경우, 이전에 놓친 핵심 불변 조건에 구체적 근거가 생긴 경우, 이 head가 드러낸 보안·개인정보·데이터
손실 위험일 때만 채택하세요. 이전 head가 "none - newly required"이거나 base가 바뀌었으면 현재 diff 전체를
리뷰하세요.
```

## 리뷰어 추가하기

일반 리뷰어들이 계속 놓치는 경계가 있으면(모바일/네이티브 코드, 결제, 마이그레이션) 영역 리뷰어를 추가합니다.
기존 스킬 폴더를 복사하고, `## 정식 지적 채택 기준 (Formal Finding Admission)` 블록은 그대로 두고, 새
체크리스트와 한 문단짜리 영역별 적용을 쓴 뒤, 라우팅 표에 행을 추가합니다. 한 번도 라우팅하지 않는 리뷰어는
지웁니다.

## 한계

- 이것은 도구가 아니라 프롬프트입니다. 품질은 모델, 리뷰어가 닿을 수 있는 맥락, 대상을 얼마나 정확히
  지정했는지에 달려 있습니다.
- 리뷰어는 양쪽으로 틀릴 수 있습니다. 깨끗한 결과가 PR이 옳다는 증명은 아닙니다.
- 몇몇 체크리스트는 웹 백엔드와 에이전트가 돌리는 저장소 쪽으로 기울어 있습니다. 그곳에서 쓰였기 때문입니다.
  예시는 자기 스택에 맞게 고쳐 씁니다.
