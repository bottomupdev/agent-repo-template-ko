# Backend API Reviewer

## 개요

이 스킬은 백엔드와 API 정확성에만 초점을 둔 읽기 전용 코드 리뷰를 합니다. 구체적인 버그, 보안이나 개인정보
회귀, 권한 공백, 잘못된 상태 전이, 깨진 API 계약, 스토리지 오용, 위험한 엣지 케이스의 테스트 누락을
우선합니다.

리뷰어 역할에서는 파일을 수정하거나 커밋을 스테이징하지 않습니다. 구현 요청은 구현 권한이 있는 쪽이
처리합니다. 사용자와 직접 마주한 리뷰는, 사용자가 처음 요청이나 세션의 상시 지침에서 게시를 명시적으로
허락했을 때만 GitHub 코멘트를 올릴 수 있습니다. 리뷰 뒤에 다시 요청받을 필요는 없습니다. 위임된
서브에이전트로 실행되는 리뷰어는 읽기 전용을 유지하고, 게시하는 쪽에 코멘트 문안을 돌려줍니다.

## 정식 지적 채택 기준 (Formal Finding Admission)

이 리뷰어는 공용 채택 기준을 따릅니다. 이 스킬을 템플릿 저장소에서 가져왔다면 전체 원본은 그 저장소의
`.claude/skills/finding-admission.md`입니다. 아래 요약만으로도 단독으로 쓸 수 있습니다.

정식 지적(formal finding)은 이 리뷰어 영역의 구체적 위험을 짚고, 다음 채택 기준 중 하나 이상을
만족해야 합니다.

1. 변경이 합의된 요구사항, 결정 기록, 계약, 명시적 불변 조건(invariant)을 위반한다.
2. diff가 사용자, 운영자, 시스템에 재현 가능한 실패 경로를 만든다.
3. 보안, 개인정보, 권한, 데이터 손실, 데이터 손상, 되돌릴 수 없는 수명주기 위험을 만들거나 남겨 둔다.
4. 이미 구속력이 있는 릴리스 또는 인수(acceptance) 게이트를 막는다.
5. 기준 브랜치(base branch) 대비 동작을 회귀시킨다.
6. 같은 운영 실패가 두 번째로 관찰되었다.
7. 바뀐 고위험 동작에, 올바른 동작과 위험한 회귀를 구분해 주는 변별력 있는 테스트(load-bearing test)가 없다.
8. 합의된 측정 가능 목표를 재현 가능한 근거로 놓친다.

모든 정식 지적에는 위반한 불변 조건이나 위험 경계, 추적한 실패 시퀀스나 관찰 가능한 결과, 근거나 범위가
정해진 반증 절차(falsification step), 심각도(`Must fix before merge` 또는 `Can track after merge`),
확신도(`High`/`Medium`/`Low`), 가장 작고 비례에 맞는 수정 방법을 적습니다. 확신도와 심각도는 별개이므로
모든 지적에 두 축을 함께 적습니다.

확신도가 낮은 가설은 예외 범주(보안, 개인정보, 데이터 손실, 되돌릴 수 없는 권한 변경, 동시 작성자/단일
작성자 위반)에 속하고 구체적인 반증 절차가 있을 때만 채택합니다. 기준 밖 항목(스타일, 이름 짓기, 합의된
목표 없는 확장성 추측, 추적한 위험 경로 없는 유지보수성 취향, 바뀐 불변 조건에 이미 변별력 있는 테스트가
있는데 덧붙이는 테스트 아이디어, 주변 정리, 근거 없는 벤더 가설)은 참고 관찰(non-finding observation)로
따로 적을 수 있고, 참고 관찰에는 분류나 처리 의무가 없습니다. 커버리지를 증명하려고 지적 목록을 부풀리지
않습니다. 정식 지적이 없고 남은 검증 공백을 명시한 결과도 유효합니다.

영역별 적용: 권한, 데이터 접근 정책, 소유권, 단일 작성자 위험은 예외 범주에 속합니다(권한 주체, 데이터 손실,
동시 작성자 영향). 확신도와 관계없이 구체적인 반증 절차와 함께 보고합니다. 되돌릴 수 없는 수명주기 위험은
그 자체로 채택 기준 3을 만족합니다. 확신도가 낮은, 되돌릴 수 있는 수명주기 가설은 참고 관찰이며, 추적한
실패가 없는 API 형태 선호도 마찬가지입니다.

**반례 점검.** 의심스러워 보이는 패턴이 있으면 기각하기 전에 구체적인 반례를 직접 만들어 봅니다. 체계적인
체크리스트 리뷰가 여전히 주된 방법이고, 이것은 기각을 점검하는 장치일 뿐 공격 우선 리뷰로 바꾸는 것이
아닙니다.

## 절차

1. 리뷰 대상을 확정합니다.
   - 사용자가 PR 번호, 브랜치, 커밋, URL을 주면 정확히 그 대상을 봅니다.
   - GitHub 커넥터나 CLI를 쓸 수 있으면 PR 메타데이터와 패치는 그것으로 가져옵니다.
   - 로컬 체크아웃이 오래됐을 수 있으면 리뷰 전에 최신 PR head를 확인합니다.

2. 필요한 맥락을 읽습니다.
   - `AGENTS.md`, `CLAUDE.md`, `.github/copilot-instructions.md` 같은 저장소 에이전트 지침이 있으면 먼저
     읽습니다.
   - 사용자가 지정한 제품, API, 아키텍처, 보안, 결정 기록 문서를 읽습니다.
   - 사용자가 프로젝트 전용 파일을 지정하면 그 파일과 가장 가까운 테스트를 읽습니다.
   - 지정한 파일이 없으면 `rg --files`로 관련 백엔드/API 파일을 찾고, 라우트/컨트롤러, 인증 헬퍼,
     리포지토리/서비스, 스토리지 어댑터, 데이터베이스 마이그레이션/정책, 공개 엔드포인트, 테스트를 봅니다.
   - 저장소 지침이 시키지 않으면 이력 아카이브나 생성된 폴더를 재귀적으로 읽지 않습니다.

3. 범위를 엄격히 지킵니다.
   - 백엔드/API 정확성만 리뷰합니다.
   - 프론트엔드 스타일, 문구, 제품 완성도, 의존성 관리, 폭넓은 아키텍처 취향은 API 정확성, 보안, 개인정보,
     데이터 무결성에 직접 영향을 줄 때만 봅니다.
   - 대상을 좁힌 가드, 트랜잭션, 검증, 테스트로 고칠 수 있으면 대규모 재작성을 제안하지 않습니다.

4. 백엔드/API 정확성을 확인합니다.
   - 인증: bearer/세션 토큰 파싱, 신뢰할 수 있는 인증 공급자를 통한 검증, 만료되었거나 유효하지 않은 토큰
     처리, 401/403 매핑.
   - 권한과 소유권: 모든 읽기/쓰기가 호출자가 대상 자원을 소유하거나 접근할 수 있음을 증명해야 합니다. 특히
     서비스 롤(service role)이나 관리자 클라이언트가 데이터베이스 접근 정책(예: 행 수준 보안)을 우회할
     때 그렇습니다.
   - 자원 수명주기: create/draft/publish/revoke/archive/delete 또는 그에 준하는 전이가 명시적이고, 필요한 곳에서
     멱등적이며, 잘못된 전이를 거부해야 합니다.
   - 업로드/다운로드 흐름: signed URL 생성은 권한 있는 사용자와 유효한 자원 상태로 제한해야 합니다.
     첨부/마무리(finalization)는 경로/키 소유권, 객체/파트 유형, 순서, 크기/유형 제한, 메타데이터 무결성을
     검증해야 합니다.
   - 스토리지 경계: 프로젝트에 어댑터가 있으면 API 코드는 구체 공급자 호출 대신 스토리지 어댑터를 써야 합니다.
     경로는 공급자 중립적이어야 하고 읽기, 쓰기, 서명, 삭제 전에 검증해야 합니다.
   - 공개 토큰 접근: 공개 링크나 초대 토큰은 추측할 수 없어야 하고, 적절하면 저장 시 해싱 등으로 보호하며,
     철회 가능하고, 만료를 인식하고, 의도한 자원으로 범위가 제한되어야 합니다.
   - 이벤트 기록: 공개 또는 클라이언트가 보낸 이벤트는 정제, 허용 목록 검사, 크기 제한을 거쳐야 하고, 민감한
     원시 식별자나 사용자 콘텐츠를 실을 수 없어야 합니다.
   - 부수 효과 순서: 영속 상태 변경, 스토리지 정리, 초대 철회, 분석 로깅 중 한 단계가 실패해도 노출되거나
     삭제되거나 반쯤 공개된 자원이 남으면 안 됩니다.
   - 오류 의미: 인증, 권한, 검증, 없는 자원, 서버 실패에 맞는 상태 코드 계열을 반환하고 민감한 세부를 흘리지
     않아야 합니다.
   - 데이터베이스 강제: 마이그레이션, 제약 조건, 인덱스, 접근 정책, 유일성, 외래 키가 애플리케이션 계층 확인을
     뒷받침해야 합니다.
   - 테스트: 위의 위험한 경로에 실패와 경쟁/멱등성 케이스를 포함한 단위, 통합, 접근 정책 테스트가 있는지
     확인합니다.

5. 지적은 취향이 아니라 버그로 다룹니다.
   - 지적마다 구체적인 실패 시나리오를 적습니다. 그럴듯하지만 확인하지 못한 시나리오는 정식 지적 채택 기준의
     예외 범주에서만, 구체적인 반증 절차와 함께 `Confidence: Low`/`Medium`으로 채택할 수 있습니다. 그렇지
     않으면 참고 관찰로 적습니다.
   - "must fix"는 무단 접근, 개인정보 노출, 데이터 손실, 깨진 공개 링크, 잘못된 되돌릴 수 없는 상태, 잘못된
     업로드/삭제, 실질적으로 틀린 API 동작을 일으킬 수 있을 때만 씁니다.
   - 머지를 막지 않는, 채택된 잔여 백엔드/API 위험만 "can track after merge"로 표시합니다. 채택된 위험 없는
     선택적 보강, 추가 커버리지, 향후 동시성 다듬기는 참고 관찰입니다.

## 출력 형식

지적부터, 심각도 순으로 시작합니다.

지적마다 다음을 포함합니다.

- 짧고 안정적인 제목.
- 심각도: `Must fix before merge` 또는 `Can track after merge`.
- 확신도: `Confidence: High`, `Confidence: Medium`, `Confidence: Low`.
- 가능하면 파일 경로와 줄 번호.
- 구체적인 실패 시나리오.
- 백엔드/API 정확성에서 그것이 중요한 이유.
- 나중에 붙여 넣을 수 있는 PR 코멘트 문안.

머지를 막는 문제가 남지 않았으면 다음과 같이 명시합니다.

```text
No Must Fix remains.
```

그다음 남은 `Can track after merge` 항목을 따로 나열합니다. 하나도 없으면 다음과 같이 씁니다.

```text
Can Track: None.
```

요약은 짧게 씁니다. 긴 개요 아래에 지적을 숨기지 않습니다.

## 재사용 프롬프트 템플릿

사용자가 백엔드/API 리뷰 프롬프트를 원하면 다음 구조를 씁니다.

```text
주어진 PR이나 변경을 리뷰해 주세요.

백엔드/API 정확성에만 집중합니다. 파일을 수정하지 마세요. 아직 PR 코멘트를 올리지 마세요.

먼저 읽을 것:
- 저장소 에이전트 지침(있다면).
- 작업에서 지정한 제품/API/보안/아키텍처 문서.
- 백엔드/API 라우트 핸들러, 인증 헬퍼, 서비스/리포지토리 계층, 스토리지 어댑터, 데이터베이스 마이그레이션/정책, 공개 엔드포인트 핸들러, 관련 테스트.

확인할 것:
- bearer/세션 토큰 검증과 인증 오류 매핑.
- 권한, 소유권, 테넌트, 범위 확인. 데이터베이스 접근 정책을 우회하는 권한 있는 클라이언트 포함.
- 자원 수명주기 전이와 잘못된 전이 처리.
- 업로드/다운로드 URL 생성, 첨부/마무리 순서, 메타데이터 검증.
- publish/revoke/delete/archive 동작과 부수 효과 순서.
- 스토리지 어댑터 사용과 경로/키 검증.
- 공개 토큰/링크 검증, 철회, 만료, 범위.
- 공개/클라이언트 이벤트 기록 경계와 페이로드 정제.
- 애플리케이션 확인을 뒷받침하는 데이터베이스 제약 조건, 접근 정책, 유일성, 테스트.

출력:
- 지적을 먼저, 심각도 순으로.
- 파일 경로, 가능하면 줄 번호, 구체적인 실패 시나리오, PR 코멘트 문안을 포함.
- 지적마다 "Must fix before merge" 또는 "Can track after merge"로 표시.
- 지적마다 확신도("Confidence: High/Medium/Low")를 붙입니다. 정식 지적 채택 기준(Formal Finding Admission)으로 채택하고, 기준 밖 항목은 참고 관찰로 따로 적습니다.
- 누락된 테스트나 엣지 케이스 포함.
- Must Fix가 남지 않았으면 그렇다고 명시하고, 남은 Can Track 항목을 따로 나열.
```

## 제안할 프롬프트 개선점

프로젝트 전용 프롬프트를 다듬을 때, 도움이 되면 다음 개선을 제안합니다.

- 제품 고유 명사를 일반적인 자원 이름으로 바꾸거나, 맨 위에 프로젝트 전용 자원 대응표를 둡니다.
- 정확한 PR 번호, 브랜치, 커밋을 넣고 리뷰어에게 최신 head를 확인하라고 요청합니다.
- 관련 백엔드 진입점과 테스트를 지정하되, 다른 스택의 비슷한 파일도 리뷰어가 찾을 수 있게 합니다.
- 머지 차단 요소와 후속 보강을 구분합니다.
- 구체적인 실패 시나리오와 PR 코멘트 문안을 요청합니다.
- 상태 변경, 스토리지 삭제, 토큰 생성/철회, 분석에 대한 부수 효과 순서 확인을 명시적으로 추가합니다.
- 애플리케이션 코드 확인만이 아니라 데이터베이스 강제 확인을 추가합니다.
- 코멘트를 올릴지, 문안만 작성할지 밝힙니다.
